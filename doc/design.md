# Qubit Event Bus 0.14 architecture status

This page records the implemented 0.14 architecture. See [the implementation architecture overview](design.zh_CN.md), the [formal SPI design in English](spi_design.md), and its [Chinese version](spi_design.zh_CN.md).

The crate exposes typed synchronous and runtime-neutral asynchronous facades over object-safe `EventBusSpi` and `AsyncEventBusSpi` contracts. Provider discovery, selection, creation, and creation-time fallback use `qubit-spi`. The crate includes synchronous and asynchronous bounded-queue local providers. It does not bundle Tokio, crossbeam, RabbitMQ, Kafka, or Redis adapters; flume is used only by a development conformance fixture.

The facade owns portable event processing: typed requests and envelopes, codecs, middleware, filtering, retries, ACK/NACK, dead-letter handling, ordering, diagnostics, and lifecycle coordination. The SPI is deliberately smaller and transports erased payloads, receives messages, settles provider-issued tokens, and closes provider resources. Capabilities describe provider-specific limits; runtime failures do not trigger silent provider failover.

Ordering is a provider contract. A subscription requesting `OrderingPolicy::PerKey` is admitted only when the provider declares `OrderingCapability::PerKey` or the stronger `PerSubscription`; a facade checks this before calling provider `subscribe`. The former subscription priority option has been removed because it had no provider or facade scheduling semantics.

`PublishReceipt` reports provider admission, not handler completion. `DestinationAdmissions` may be empty or contain accepted, filtered, and rejected destinations. A mixed result is still a successful receipt; retrying the whole event may redeliver it to accepted destinations. `publish_all` is best-effort and non-atomic. `EventId` is a portable event identity (UUID v4 by default); `qubit_id::Id` is only a bus-local subscription object ID. Sync and async middleware are separate types and a facade rejects middleware for the other execution model. Async subscription consumption is caller-driven and does not spawn a task, but its owned delivery futures use a bus-wide `max_in_flight` admission limit; different ordering keys may progress concurrently while a key remains ordered. Dropping `run()` pauses owned work for a later run or bus shutdown to resume.

`PublishReceipt::check_admission` evaluates only that receipt's reported admissions, with either an at-least-one-accepted or at-least-one-accepted-and-no-rejections requirement. It has no publication side effect and cannot undo or retry the original call. Per-facade `PublishMetricsSnapshot` counters report public publish attempts, errors, interceptor drops, opaque accepts, zero-destination receipts, and accepted/filtered/rejected destination totals. Fields are loaded independently, so a concurrent snapshot is not a transactionally consistent instant; none of these counts reports handler completion. A synchronous `Subscription` handle does not cancel on drop: callers must invoke `cancel()` or shut down the bus.
`PublishReceipt::admission_outcome` centralizes the classification of opaque acceptance, accepted destinations, partial acceptance, no acceptance, empty destination snapshots, and interceptor drops. It is a view of the completed receipt, not a handler result or retry instruction. Use `acknowledgement()` when per-destination identity and rejection details are needed.

The synchronous local provider gives every subscription one blocking receive worker. A measured Linux sample reached 133 process threads at 128 subscriptions, with a 5.36-second median to cancel and immediately shut down that sample. The async local provider uses waker-based receives and creates no receiver thread per subscription. Provider-level `Ephemeral` queues are discarded on close/drop; only cancellation of `AsyncSubscription::run` while retaining its handle preserves facade-owned tasks. A same-host seven-sample comparison measured one process thread and 0.085 ms p95 close/shutdown for 128 idle async subscriptions. See the temporary execution report for raw samples; these values are not capacity guarantees.

The local provider binds a topic name to one native Rust payload type while subscriptions are active. Per-subscription capacity defaults to 1,024 and provider-wide outstanding capacity defaults to 65,536 delivery items. Both cover queued and unsettled deliveries; Retry preserves a delivery's reservation. The provider-wide limit counts accepted destination deliveries per provider instance, not payload bytes, and full destinations are individually rejected in the acknowledgement. Sync `EventBus::wait_for_idle` reports provider queue and settlement state, while `wait_for_received_deliveries` reports only work already received by that facade. The async facade exposes only the latter guarantee.

## Local provider routing and resources

In the 0.14 implementation, `BusState` indexes live subscriptions by topic. Publish snapshots only the requested topic's queues, preserving subscription-ID order, then releases the global state lock before interacting with queue locks. Idle waits use the same topic-scoped lookup; shutdown snapshots all live queues. This reduces unrelated-topic work during publish and idle checks without changing the SPI contract.

Each subscription owns a bounded queue. Its configured capacity counts queued deliveries and deliveries already received but not settled. A retry reuses the original reservation, so repeated retries do not create additional capacity. Internally, 0.14 keeps a FIFO lane per ordering key, rotates ready lane heads, and orders delayed lane heads in a versioned min-heap. A delayed head blocks successors in its own lane, while unrelated ready lanes remain eligible. When obsolete delayed-heap entries exceed the greater of the live-head count and a fixed slack of eight, the heap is rebuilt; this bounds stale scheduling metadata while keeping delayed-head lookup efficient. These indexes trade extra bookkeeping for avoiding repeated scans across a long blocked queue prefix.

The synchronous receive SPI remains blocking: every synchronous subscription has a receive worker thread. In a 6-CPU Linux sample, subscriptions 1/16/128 peaked at 6/21/133 process threads. Median creation times were 0.226/1.592/7.551 ms and median cancel plus immediate-shutdown times were 0.285/651.543/5359.302 ms. Teardown ranges were wide and unrelated host load was present, so these values describe one observation only; `cargo bench --bench local_threads` reruns the measurement for both local providers.

The benchmark decision retained topic buckets and indexed queues based on local comparisons, not service-level guarantees. `cargo bench --bench local_scale -- publish` measured p95 improvements of 70.8% and 67.2% in two 32-topic/16-subscriber cases, a 4.6% improvement in the 1-topic/1-subscriber case, and a 21.3% p95 slowdown for 1 topic/128 subscriptions in one sample. With a depth-1024 queue and a long blocked prefix followed by a ready suffix, `cargo bench --bench local_scale -- receive` reduced median receive p95 from 42,654 ns to 590 ns with 16 ready keys and from 41,590 ns to 539 ns with 1 ready key. These are host-specific comparative results; they do not predict another workload or machine. Both local providers are non-durable and in-process.

Settlement repeats with the same token and disposition must be idempotent; conflicting dispositions must fail. Async settlement may be retried after cancellation with that same token. `Immediate` shutdown stops intake and drops not-yet-started queued work, but waits for active user code, settlement, receiver close, and provider shutdown so errors can be returned. It cannot forcibly interrupt a running Rust handler. Synchronous graceful shutdown uses one background coordinator per bus: the caller's deadline includes admitted publish/subscribe calls, worker drain and close, and provider shutdown. After `TimedOut`, the bus stays in `Closing`; new operations fail while the coordinator continues, and a later call can await its result or strengthen the attempt to `Immediate`. A blocked synchronous SPI method or handler can keep the coordinator alive. Async deadlines use `qubit-clock`'s `Timer`; the default is the standard monotonic timer and callers may inject another timer through `with_timer` or `with_config_and_timer`. Dropping an async shutdown future may leave provider side effects in progress, so providers must support idempotent retries.

Dropping an `AsyncSubscription::run` future pauses its owned delivery tasks for a later `run` call; dropping the subscription handle itself disposes the paused session and receiver. The built-in async local provider discards pending and in-flight deliveries when its ephemeral receiver closes or drops; resubscribing with the same subscriber ID starts empty. This disposal is not an acknowledgement to a durable system. Call `AsyncSubscription::close().await` when deterministic async cleanup and close errors are required.

Publish terminal-error handlers receive `PublishFailureContext<T>`, which shares the payload and exposes event metadata without requiring `T: Clone`. They run after a direct SPI publish failure when no retry policy is configured, or after configured retries reach terminal failure—not for preflight errors. Applications that use advanced retry configuration depend directly on `qubit-retry`; this crate does not re-export it.
